# HR Talent System — цифровой профиль сотрудника

Система поддержки кадровых решений: подбор внутренних кандидатов на зарубежные
назначения с проверяемым расчётом каждого балла.

Интерфейс на трёх языках: **русский / қазақша / English**.
Развёртывание — полностью on-premise.

---

## Ключевые принципы

| Принцип | Как реализовано |
|---|---|
| **Детерминированный расчёт** | Стаж, опыт и баллы считает backend. LLM в расчёте нет. |
| **Объяснимость каждого балла** | Карточка расчёта: требование → факт → M → вес → вклад. |
| **Методология отделена от кода** | Веса, функции соответствия, компенсации и пороги — версионируемые строки в БД. |
| **Историчность** | Карьера хранится интервалами; оценки не перезаписываются. |
| **Справочник вместо текста** | Подразделение, должность, язык, компетенция — только из справочников. |
| **Ошибка до БД** | Уровень B3 в шкале CEFR отклоняется с понятным сообщением. |
| **Человек решает** | Системный ранг неизменяем; расхождение требует причины. |
| **Псевдоним по умолчанию** | Шорт-лист открывается с кодами; раскрытие Ф.И.О. журналируется. |

---

## Быстрый старт

Одна команда поднимает всё: запускает Docker, собирает образы, дожидается
готовности API и интерфейса и наполняет пустую базу справочниками, методологией
и демонстрационным кейсом.

**Windows (PowerShell):**

```powershell
.\deploy.ps1 up
```

**Windows (cmd.exe):**

```cmd
deploy.bat up
```

**Linux / macOS / Git Bash:**

```bash
./deploy.sh up
```

### Команды

| Команда | Что делает |
|---|---|
| `up` | Собрать, запустить, дождаться готовности, наполнить пустую базу |
| `status` | Состояние контейнеров, endpoint'ов и базы |
| `test` | Приёмочный набор из 79 проверок |
| `logs` | Журналы в реальном времени |
| `seed` | Повторно загрузить справочные данные |
| `down` | Остановить (данные сохраняются) |
| `reset` | **Удалить все данные** и собрать заново (с подтверждением) |

| Что | Адрес |
|---|---|
| Интерфейс | http://localhost:5173 |
| API + Swagger | http://localhost:8000/docs |
| PostgreSQL | localhost:5432 (postgres / postgres) |

### Учётные записи

| Логин | Пароль | Роль | Доступ |
|---|---|---|---|
| `admin` | `admin` | Администратор | Полный: справочники, методология, ввод данных, решения, аудит |
| `user` | `user` | Просмотр и анализ | Чтение профилей и вакансий, запуск подбора, карточки расчёта |

Разграничение проверяется на сервере: любой запрос на изменение, кроме запуска
подбора, требует роли администратора. Скрытые в интерфейсе кнопки — это
удобство, а не граница безопасности.

> **Перед реальной эксплуатацией** задайте переменную окружения `AUTH_SECRET`.
> По умолчанию используется фиксированное значение, пригодное только для стенда.

## Модель данных

Нормализованная, 1:N. Никаких «200 столбцов в таблице Employee».

```
employees
├── employee_education        (уровень, ВУЗ, специальность, годы)
├── employee_languages        (язык, шкала, уровень, подтверждение, срок)
├── employee_training         (курс, направление, даты, сертификат)
├── work_experience  ← карьерный путь; источник ВСЕХ показателей стажа
├── assessment_sessions
│   └── competency_scores     (справочник компетенций × баллы сессии)
└── employee_metrics          (производные величины, только расчёт)
```

Персональные данные: Ф.И.О., дата и **место рождения**, страна рождения,
**национальность**, табельный номер, обезличенный код, дата приёма,
текущие должность и подразделение, статус профиля.

Каждая запись `work_experience` фиксирует **job family**, тип подразделения и
страну **на момент периода** — поэтому «опыт маркетолога» определяется по
функции, а не по поиску слова «маркетолог» в названии должности, и позднейшая
реорганизация не переписывает историю задним числом.

### Что система считает сама

Пользователь вводит только интервалы работы. Дальше:

```
company_experience_years              8.0
function_experience_years:MARKETING   5.0
function_experience_years:ANALYTICS   3.0
org_unit_experience_years:REGIONAL    3.0
org_unit_experience_years:HQ          3.0
org_unit_experience_years:FOREIGN     2.0
country_experience_years:AT           2.0
```

Пересекающиеся периоды объединяются, а не суммируются дважды.
Дочерние job family засчитываются родительским (Marketing Analytics ⊂ Analytics).

## Гибкость: что редактируется без изменения кода

Всё перечисленное — данные, доступные через раздел **Справочники**:

- страны, национальности, языки, шкалы языков и их уровни;
- уровни и направления образования;
- **job families** (в том числе вложенные);
- типы подразделений, грейды, типы обучения;
- **шкалы оценивания** (1–5, 0–10, любая своя);
- **компетенции** — профессиональные и психологические;
- **типы требований** с описанием схемы условия;
- оргструктура и должности.

Добавление компетенции «Negotiation» — одна строка в справочнике.
Схему БД менять не нужно.

### Методология

Раздел **Методология** хранит версионируемые модели скоринга:

- **Функции соответствия M** — `step_absolute`, `step_ratio`, `linear`,
  `boolean`, `level_scale`. Ступени задаются точками перегиба:

  ```json
  [{"min_ratio":1.0,"m":1.0},{"min_ratio":0.67,"m":0.75},
   {"min_ratio":0.33,"m":0.40},{"min_ratio":0.0,"m":0.0}]
  ```

- **Компенсационные таблицы** — прямой опыт 1.00, профильное образование 0.75,
  только курсы 0.30 и т. д.
- **Пороги готовности** — Ready Now ≥ 90, Ready ≤ 6 мес. ≥ 80, …

Утверждённая модель неизменяема. Чтобы поменять правило — создаётся копия с
новой версией. Прежние запуски подбора навсегда привязаны к своей версии,
поэтому вопрос «почему кандидат получил такой балл в прошлом месяце»
восстанавливается.

## Формула

```
Score = Σ (W_i × M_i) / Σ W_i × 100      M_i ∈ [0, 1]
```

Классы требований:

| Класс | Поведение |
|---|---|
| **Critical Must** | Невыполнение исключает из основного шорт-листа |
| **Must Have** | Высокий приоритет, допускается компенсация |
| **Nice to Have** | Повышает балл, но не исключает |

Кандидаты, не прошедшие критические требования, не исчезают: они выводятся
отдельным списком «потенциальные после развития» с указанием, что именно
не выполнено.

## Демонстрационные данные

`seed_data.py` воспроизводит сценарий из постановки задачи: вакансия
**«Менеджер по маркетингу — Австрия»** с восемью требованиями (сумма весов 100)
и пять кандидатов А–Д.

Кандидат **В** не работал аналитиком, но прошёл профильный курс — это случай
компенсации. При модели 1.0 он получает 4.5/15, при модели 1.1 (значение
`training_only` изменено на 0.60) — 9/15, без единой правки кода.
